# Руководство оператора

Установка, зависимости и профили: [README.md](README.md). Скилл запускается явно, рядом с v2, и не требует hooks или Loop Review.

## Режимы dev-версии

Аргументы передаются одному скилу; отдельных slash-команд установщик не создаёт:

- `$orchestrate-development-v3 plan <задача>` — подготовить план без реализации.
- `$orchestrate-development-v3 run <задача>` — выполнить задачу; маленькие изменения остаются прямыми.
- `$orchestrate-development-v3 resume <этап>` — сверить текущие файлы, владение и доказательства, затем продолжить.
- `$orchestrate-development-v3 diagnose` — показать расхождения установки без исправлений.

Обычный запрос на выполнение равнозначен run. Основной root-маршрут — Terra High; Luna Max временно поддерживается как совместимый root с тем же контрактом. Диагностика доступна без запуска агентов; её необязательный скрипт требует Python 3.11+. В source-only checkout отсутствие установленной копии ожидаемо.

Для сравнения установки с dev-исходниками:

```sh
python scripts/orchestration_doctor.py diagnose --project <проект> --package <dev-пакет>
```

Эта команда ничего не устанавливает. Контракты проекта, план этапа, Goal и capsule имеют разные сроки действия: [контекст и восстановление](references/CONTEXT_AND_RESUME.md). Снимок входов охватывает явно перечисленные файлы; неизменность байтов не доказывает полноту тестов или неизменность окружения.

## Порядок работы

1. Root на Terra High по умолчанию определяет результат, границы этапа, требования, владельцев изменений и критерии приёмки. Уже запущенный root на Luna Max продолжает работать по тому же контракту совместимости.
2. Astra Low изучает связанный код, составляет актуальный опорный план и определяет несколько содержательных проверок результата. Два-три сценария — ориентир для ограниченной задачи, не лимит большого этапа.
3. Astra реализует результат, проверяет его и возвращает компактный EVIDENCE_CAPSULE. Обязательного test-first и тестов каждой мелкой функции нет.
4. Root интегрирует результат. По риску или обязательной границе проекта назначает независимое внутреннее ревью Sol Medium. Исправления получает Astra или Luna XHigh.
5. Luna XHigh validator выполняет финальную валидацию стабильного этапа: проверяет запуск сценариев, окружение, пропуски, логи и нужные артефакты. Сам продукт не исправляет. Root принимает этап на основании свидетельств.

## Ревью и валидация

Sol возвращает доказательные замечания без числовых оценок и автоматического цикла раундов. Новый полный проход требуется при существенном изменении поведения или границы риска. Terra проверяет один спорный факт и не запускается как обязательный второй ревьюер.

Обычная стадия: реализация → адресные проверки → интеграция → финальная валидация → приёмка.

Стадия с ревью: реализация → адресные проверки → стабильная интеграция → Sol → исправления → затронутые проверки → финальная валидация → приёмка.

Контракты: [внутреннее ревью](references/INTERNAL_REVIEW.md), [финальная валидация](references/FINAL_VALIDATION.md).

## Границы

Проектные правила архитектуры, безопасности, обязательных тестов и публикации сохраняются. Исключение для механизма Loop Review закрепляется в AGENTS.md проекта; [готовый фрагмент](docs/AGENTS.integration.md). Установщик эти инструкции не изменяет.

Телеметрия и глобальная защита расходов устанавливаются отдельно, если нужны. Их отсутствие не блокирует workflow. Root не вызывает ledger отключённого orchestration guard. Необязательный Spark использует [включённый адаптер](references/SPARK_ADAPTER.md); основной workflow может работать без него.
